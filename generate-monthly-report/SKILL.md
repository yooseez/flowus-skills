# 生成月报

当用户说"生成月报"、"上月月报"或要求生成月报时，自动执行以下流程。

## 执行步骤

### 1. 确定月份

- **月报覆盖一个自然月：1日到月末**（如7月报为7月1日到7月31日）
- 默认生成"上月"的月报
- 月份格式：`YYYY-MM`（如 `2026-07`）
- 示例：今天是2026年8月15日，则上月为2026年7月，月份参数为 `2026-07`

### 2. 提取数据

运行参数化提取脚本（位于本技能目录下）：

```bash
python "<技能目录>/extract_month.py" <YYYY-MM> <output_path>
```

示例：
```bash
python "C:\Users\HONOR\.trae-cn\skills\generate-monthly-report\extract_month.py" 2026-07 "C:\Users\HONOR\.trae-cn\skills\generate-monthly-report\month_data.json"
```

**⚠️ 人员完整性校验**：脚本运行后检查输出，如果出现 `WARNING: Found unmapped persons!`：
1. 根据输出的 uid，在 `extract_month.py` 的 `USER_MAP` 中添加映射（格式：`uid → "岗位 姓名"`）
2. 重新运行提取脚本
3. **不得带着警告直接生成报告**

### 3. 生成 Word 文档

确保 `docx` npm 包可用（首次使用时运行 `npm install docx`），然后执行：

```bash
node "<技能目录>/gen_month_docx.js" <YYYY-MM> <data_file>
```

示例：
```bash
node "C:\Users\HONOR\.trae-cn\skills\generate-monthly-report\gen_month_docx.js" 2026-07 "C:\Users\HONOR\.trae-cn\skills\generate-monthly-report\month_data.json"
```

- 生成脚本内置自然月过滤，即使数据文件包含其他月份的记录也只统计目标月份
- 输出文件自动保存到：`D:\华为家庭存储\工作文档\TIU管理\周报月报\项目开发团队月报-YYYY年M月D日-M月D日.docx`（同年仅显示一次年份，跨年两个日期都显示年份）

### 4. 完成后

告知用户报告已生成，附上文件链接，并简要列出数据概览（记录数、总工时、工作日数、参与人数、涉及项目数）。

## 关键规则

### 人员映射
- FlowUs "人员"字段是 formula 类型，API 返回 null，无法直接读取
- 通过记录的 `created_by.id`（uid）配合 `USER_MAP` 映射到"岗位 姓名"
- USER_MAP 中的完整映射参考 `extract_month.py` 中的注释
- 添加新成员时：在 USER_MAP 中添加 `uid → "岗位 姓名"`

### 报告结构
1. **封面**（纵向）：标题"项目开发团队月报（YYYY年M月）"或"项目开发团队月报"（跨月时）+ 实际数据日期范围 + 统计概览表
2. **一、人员投入统计**：表格（显示"岗位 姓名"）
3. **二、项目投入统计**：表格（参与人员列只显示姓名，不显示岗位）
4. **三、人员×项目投入矩阵（工时）**：横向表格（显示"岗位 姓名"，人员列宽14%）
5. **四、人员月度工作总结**：按人员+项目汇总，系列任务显示详细列表
6. **五、项目月度工作总结**：按项目汇总，简化为类别名称

### 工作总结格式
- 人员行格式：`岗位 姓名  工时数工时（合计X人天），总共填报X次`
- 项目行格式：`项目名  工时数工时（合计X人天），X人参与（姓名1、姓名2）`
- 工作项编号显示，系列任务格式：`XX相关{后缀}：包括A、B、C等`（冒号分隔）
- 优先从进展说明提取工作内容，过滤纯进度状态（如`100%`、`（未开发）`）
- 进展说明不明确时，回退到任务名称字段
- 相似任务自动合并（共同前缀≥4字合并为"XX相关{后缀}"）
- 3+项共享2字前缀的自动归组为系列
- **动态后缀规则**：根据任务性质自动确定后缀
  - 全部开发相关（含"开发""编写""对接""优化"等）→ `功能开发`
  - 全部问题处理相关（含"问题""修复""排查""报错"等）→ `相关问题处理`
  - 既有开发也有处理 → `功能开发及相关问题处理`
  - 均不匹配（如"部署""专项""要点""考核"等）→ `功能`
  - 该规则适用于所有任务名称，避免全部显示为"相关问题处理"
  - 使用 `combineSuffix` 函数合并前缀和后缀，自动避免"相关"重复（如"XX相关相关问题处理"→"XX相关问题处理"）
- **运维预处理规则**：
  - 以"处理"开头的任务（如"处理客户人员""处理运维问题"等）直接归类为"运维及其他工作"
  - 不参照6项判断规则，不论多少个都归为运维
  - 如果其他任务已包含"运维"字样，则静默吸收不单独列出
  - groupThemes中跳过"处理"前缀的项，防止被重新分组
- **系列任务显示规则**：
  - 少于6项：显式列出，格式 `XX工作部署、专项工作、工作要点等{后缀}`（去掉公共前缀）
  - 6项及以上：使用通用名称 `XX相关工作：包括A、B、C等`（不再区分后缀）
  - 该规则同时应用于 `groupThemes`（2+字公共前缀，3+项）和 `mergeByPrefix`（4+字公共前缀，2+项）
  - 使用 `isMeaningfulPart` 过滤无意义部分（如"开发""模块开发"等），无意义时回退到 `combineSuffix` 格式
  - `stripActionSuffix` 会剥离尾部"模块"和"迁移"等动作词，返回空串而非原文
- **分组对合并规则**（`mergePairedGroups`）：
  - mergeByPrefix后，对已有分组项（含"等"+"后缀"或"相关"）按2+字公共前缀合并
  - 解决同一主题被不同长度前缀拆分的问题（如"法治工作部署、要点等" + "法治专项工作相关功能开发" → "法治要点、考核、工作部署、专项工作等功能开发"）
  - 从显式列出格式和回退格式中提取有意义部分，合并去重后重新生成
- **分类优先级规则**（`classifyWork`）：
  - "运维"检查优先于"问题"检查（防止"生产运维问题"被误分类为"问题处理"）
  - 确保"运维及其他工作"能正确吸收"生产运维问题相关问题处理"等子类
- 人员总结中保留原始格式和详细列表
- 项目总结中：<6项显式列出简化为`XX相关{后缀}`，≥6项保持`XX相关工作`
- 过滤纯提交脚本/代码类任务（如"提交脚本以及代码到公司环境"）
- 子类被父类覆盖时自动合并（如"运维相关问题处理"被"运维及其他工作"吸收）
- 不列出每日任务标签，因为任务标签加起来不等于总工时

### 页面布局
- 封面Section：纵向（Portrait）
- 正文Section：横向（Landscape），尺寸 16838×11906 DXA，margin 720
- 封面概览表宽度：6000 DXA
- 一、二表宽度：9000 DXA
- 三矩阵表宽度：100% PERCENTAGE（不用DXA，不用FIXED）
  - 人员列：14%，合计列：8%，项目列：Math.floor((100-14-8)/项目数)%
