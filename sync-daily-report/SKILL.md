### 3. 认证：`FLOWUS_TOKEN` 必须在**运行账户**里

- 三个脚本**都不读注册表**（winreg 兜底只存在于周报/月报的提取脚本，2026-09-25 起集中在 `_shared/extract_common.py`，入口 `extract_week.py` / `extract_month.py` 只是薄封装）——它们是**靠子进程继承当前进程的环境变量**把 `FLOWUS_TOKEN` 传给 CLI 的。所以：
  - **Windows 任务计划程序**：变量要设在「运行任务的那个账户」下；用 SYSTEM / 服务账户跑时看不到你登录用户的环境变量 → 改在任务里显式设，或改用系统级变量。
  - **Linux cron / systemd**：`cron` **不读 `.bashrc`**。写进 `/etc/environment`、systemd 的 `Environment=FLOWUS_TOKEN=...`，或干脆在 cron 行内联 `FLOWUS_TOKEN=xxx /usr/bin/node ...`（多任务共用时建议前两种）。
- 自检：`"<CLI>" doctor` → 期望 `authenticated=true / authMode=static / tokenSource=env / user.name=trae2`。
- ⛔ **不要执行 `flowus.exe login`**：网页授权会重新签发令牌并作废同族旧令牌（曾因此顶掉 TRAE 侧 MCP 令牌）。

### 4. 定时排程（关键：脚本自己算日期，不依赖服务器时区）

- 四个时刻（**北京时间**）：`9:00`、`10:50`、`13:35`、`17:20`，命令见上文「一天四次」表；**只有 17:20 那条带 `今天`**，四条都带 `--push --auto`。
- `beijingToday()` 是 `Date.now() + 8h` 硬算的 → **服务器时区随便设，日期判定都不会错**；但**触发时刻由调度器按本机时区解释**，所以非 UTC+8 的机器要在 crontab 头部写 `TZ=Asia/Shanghai`（Windows 计划任务则按本机时区折算时刻）。
- Linux 示例（4 行，命令必须绝对路径、不要 `cd`）：
  ```cron
  TZ=Asia/Shanghai
  ###############################################
  # 需要 TZ 与 FLOWUS_TOKEN；cron 不读 .bashrc
  FLOWUS_TOKEN=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
  0  9  * * * /usr/bin/node /opt/daily-report/notify_missing.js --push --auto
  50 10 * * * /usr/bin/node /opt/daily-report/notify_missing.js --push --auto
  35 13 * * * /usr/bin/node /opt/daily-report/notify_missing.js --push --auto
  20 17 * * * /usr/bin/node /opt/daily-report/notify_missing.js 今天 --push --auto
  ```
- Windows 计划任务：程序＝node 绝对路径，参数＝`"<脚本目录>\notify_missing.js" --push --auto`，**起始位置＝脚本目录**（`__dirname` 定位同目录的 `sync_report.js` / `server.js`）。
- `--auto` 节流用 `Date.now()` 绝对时间比差，跨时区无影响；阈值 60 分钟，四条任务共享同一个状态文件（`mode` / `targetDate` / `synced` / `ts` / `at` 五个字段，其中 `synced` 用于「该日已同步完成 → 跳过」）。
- ⚠️ **状态文件必须可被所有定时任务读写到**：若四条 cron / 计划任务跑在不同系统账户下（Windows 计划任务用 SYSTEM 跑时落在 `C:\Windows\System32\config\systemprofile\.workbuddy\`），`os.homedir()` 会指向不同目录 → 节流与「已同步」判定全部失效（表现为每次都真跑、重复催报）。排查：以**运行任务的那个账户**执行 `node -e "console.log(require('os').homedir())"`，确认与写入的位置一致。

**脚本输出中找"模式: auto"还是"模式: confirm"：**

- **confirm（需人工确认）**：不要贴明细表。启动确认页面：
  ```
  node "<本 skill 目录>\server.js" <目标日期>
  ```
  目标日期从脚本输出第一行"目标日期: XXXX-XX-XX"获取。
  若 8790 端口被占用，先停掉旧进程再启动。
  用 present_files 打开 `http://localhost:8790`，告知用户在页面上操作。

## 📋 回复表格的合并行显示规范

同一人当天有多条日报条目、需在表格中体现「当日合计」时（用户要求，2026-09-20 定稿）：

- **禁止用 `↑` 等箭头/符号代替文字**：曾用 `↑` 表示"与上一条合并计算"，被用户误读成数字 **1**，产生歧义。
- 标准写法：第一条写实际合计（如 `8h`），后续行写 **`与上一条合并（两条合计 8h）`**；横向空间紧张时可简写为 `与上一条合并`。
- 需提示异常时直接写出数值，如 `与上一条合并（两条合计 7h ⚠️）`，不要用符号顶替合计值本身。
- 该规范适用于所有自制汇总表/说明表，不限于 auto 模式明细表。

## 📝 备注同步（任务名称 + 进展说明）

工时同步的同时，脚本会把日报的「任务名称 + 进展说明」写入当天模版的**备注**字段（title 类型），格式固定为多行文本：

```
任务名称：XXX
进展说明：
<日报进展说明原文，多行原样保留>
```

规则（`sync_report.js` / `server.js` 内置，auto 与 confirm 模式都会执行）：

- 仅对**单条模版记录且当天有对应日报条目**的行写入；多条模版、无日报条目的行不动。
- **备注已有内容（含人工填写）一律跳过，绝不覆盖**——重复执行是幂等的。
- 进展说明取自日报「进展说明-1/2/3」字段，与「项目-i/任务名称-i」同槽位对应；多条去重后换行拼接。
- 项目匹配与工时同步共用同一套逻辑（含 浙能法务→浙能法务二期 别名、集团采购/中国诚通挂「其它项目」按【父记录】子项目二级匹配）。
- 输出行 `备注同步: 写入 X / 已有跳过 Y / 无进展跳过 Z`，写入明细逐条打印 `[备注写入] 人员 / 项目`。

## ⚠️ 强制确认规则：任一人当日总工时 ≠ 8 小时

汇总行中的「不等于8小时」筛的是**每人当日日报总工时 ≠ 8 小时**（不足 **或超过**）：

- 只要有一人合计 ≠ 8h（例如 2.5h+5.5h=8h 正常；但 3h+5h=8h 正常，**6h+10h=16h 这类异常累加会命中**），模式强制为 **confirm**，生成确认页面人工核对，**绝不自动写入**。
- 判定带 1e-9 容差，2.5h+5.5h 这类浮点累加不会误判。
- confirm 模式下脚本不会写任何数据；必须走确认页面人工提交。

## ⚠️ 读取失败会自动诊断（不再静默返回 0 条）

**⭐ 触发来源判定：为什么不能识别"手动点运行"，以及怎么办（2026-09-24 定稿）**

- **结论：识别不了。** 2026-09-24 实测：在自动化面板点「运行」时，平台下发的指令包装与定时触发**完全一致**——`<automation_system_reminder>`、`<user_query>` 一字不差，进程环境里也**没有任何标记变量**（已枚举全部 187 个环境变量，无 `AUTOMATION_*` / `TRIGGER_*` / `RUN_MODE` 之类）。所以"本次是手动点的"这件事，**从入口侧拿不到**。
- **改用时点判定**：由定时任务把计划时刻显式写进命令（`--scheduled-at=17:20`），脚本自己比对当前北京时间：

  | 当前时刻 vs 计划时刻 | 判定 | 行为 |
  |---|---|---|
  | 相差 ≤ 容差（默认 15 分钟） | 定时触发 | `--auto` 生效：节流 + 已同步护栏照旧 |
  | 相差 > 容差 | 手动触发（面板手点 / 平台延迟补跑） | `flags.auto` 置 false → **降级为 manual**：不查节流、不受护栏，真实查询并推送，状态记 `mode=manual` |

  降级时脚本会打印两行：
  ```
  ⓘ 触发来源判定：当前 18:10，计划 17:20（容差 ±15 分钟，相差 50 分钟）
    → 判定为手动触发（面板手点 / 延迟补跑）：本次不受节流限制，真实执行
  ```
- **不传 `--scheduled-at` 时行为完全不变**（向后兼容，白天三次不受影响）。容差只影响"是否放行"，不会影响定时那次的正常执行——17:20 定时触发永远落在窗口内。

**⭐「一人一群」定向推送 —— 让「已交日报的人」不再被打扰（2026-09-22 用户选定）**

群机器人做不到"只发给某一个人"（消息会落到群里所有人），但**可以让每个群只装一个人** —— 效果等同私聊，且照样绕开可信IP。

- **为什么最少是「你 + 他」2 人**：企微**不支持建只有自己的群**（建群时必须至少勾选 1 个成员），所以每个专属群＝你 + 该成员，共 2 人。你自己的号在每个群里，因此你也会收到全部提醒（这正好，你本来就是盯的人）。
- **"必须 3 人以上"的说法以实测为准（2026-09-22 核查）**：官方《如何设置「消息推送」》只在条件里要求"**内部群聊**（外部群不支持）"，常见问题把"群聊无法添加"的原因逐条列全——外部群 / 开启仅群主管理 / 管理员停用了「消息推送」应用 / 不在"可创建消息推送的成员"白名单 / 已发布但手机端不支持添加 —— **均不含人数下限**；但网上有文章称"群机器人仅支持 3 人以上的内部群"，两者冲突，文档定不了论。→ **判定方法（30 秒）**：手机建一个只勾 1 人的群，能建出来就是 2 人群；再进群 →「…」→「消息推送」→ 添加，能成功即完全成立。**若 2 人群确实加不上**，兜底：群里放第三个人＝**你自己的另一个账号**（如张威，不在名册内，收到的也只是你自己的提醒）。
- **别想着用接口自动建群**：`appchat/create` 要求自建应用 + **可见范围＝根部门** + 出口 IP 在**企业可信IP** 内，当前环境仍是 `60020`（2026-09-22 实测，出口 IP `114.94.40.209`），走不通；一人一群只能手工建。（不过该接口文档写明 `userlist` **至少 2 人**，可作为"企微本身存在 2 人群"这一形态的旁证。）

**🔍「某人收不到提醒」怎么排查（2026-09-23 整理）**

群机器人是**发到一个群**，不是发给某个人。这是整套机制最容易误解的地方——**不存在"给他开通一下就能收到"这回事**，前提是他本人是那个群的成员。按下面顺序查，前三步就能解决 90% 的情况：

| 步骤 | 查什么 | 结论 |
|---|---|---|
| 1 | 他的名字在不在 `wxwork.json` 的 `userWebhooks` 里？ | **不在 → 他根本没有专属群，必然收不到。** 需要新建一个专属群（企业微信里建群 → 群设置 → 群机器人 → 添加 → 复制 Webhook），把地址按「键＝姓名」加进 `userWebhooks`。**键必须和模版表「负责人」完全一致** |
| 2 | 是不是在追已被撤回的那几条？ | 撤回后所有人都看不到，**属正常，不用修**。今天是 2026-09-23，此前 13:47 误发的一批已被用户用管理员身份撤回 |
| 3 | 他是不是那 3 人之一，但说"手机和电脑都没有"？ | 走下面三步自查 |

**确实在群里却看不到时的三步自查**（让本人在手机上操作）：

0. **⭐ 先做 10 秒定方向的动作（2026-09-23 周彦佐案例补充）**：让本人打开**个人微信**，**点进**他那个专属群会话（不是看会话列表），看 17:21 / 19:39 那样的机器人消息**在不在里面**——
   - **在** → 消息其实到了，只是**没弹提醒** → 查免打扰（群会话右上角 / 插件设置里的「消息免打扰」）和微信本身的通知权限，不用折腾别的；
   - **不在**（列表最后一条还停在进群提示）→ **插件同步断了**，走下面 1/2/3 步。⚠️ 别只看会话列表的预览就下结论，也**别被"最后一条是 XX邀请你加入群聊"骗了**——那可能只是较新的机器人消息被管理员撤回后的残留，也可能是真的没同步过来，**点进去看才算数**。
1. **群是否免打扰** —— 进专属群看右上角铃铛有没有划掉。官方文档明确：会话设了免打扰，微信插件也不会有角标。
2. **⭐ 插件内的成员级「接收企业消息」开关（官方接收前提第一条，每人独立，头号嫌疑）** —— 微信插件主界面 → **右上角 → 设置 → 「接收企业消息」**打开。这是官方 FAQ 给的第一条排查项（work.weixin.qq.com/api/doc/90000/90136/90315），别人开了不代表他开着。
3. **有没有关注「微信插件」** —— 个人微信 → 通讯录 → 找本企业那个企业号。没关注就收不到任何企业消息。需管理员到【我的企业 → 微信插件】生成邀请二维码让他扫（**二维码 7 天有效**）。
4. **企业微信 App → 设置 → 消息通知** —— 「仅在企业微信中接收消息」勾了的话，消息只停留在企业微信里，不会同步到个人微信。**注意：此选项可能因版本/平台不显示（周彦佐的 iPhone 上就没有），不能因"没看到这选项"就排除。**

**⭐ 官方兜底手段**（前几步都过了还不行）：**取消关注微信插件再重新关注**（插件 → 右上角 ··· → 不再关注 → 重新扫邀请码），并把微信更新到最新版——这是官方文档明确的最后手段，实测场景里能解决大部分"设置都对但就是不同步"的悬案。

- 本机在外网**完全不可达**：用 check-host.net 从多组境外节点探测 9021 端口，**4/4 全部 `Connection timed out`**（换网前对旧 IP、换网后对真实出口 IP 各测一轮，结果一致）。**Windows 防火墙不是原因** —— `node.exe` 在 Public 配置文件下已有 Allow/Any 端口规则；卡点是**没有入站通道**（当时连的是手机热点 `192.168.43.x`，运营商侧 NAT，无法做端口映射）。
- **出口 IP 不稳定且多出口**：同一台机器上 `curl` 与 Node 拿到的 IP 都不一样（curl 优先 IPv6 `240e:...`，Node 走 IPv4），企微侧看到的出口 IPv4 还随网络切换而变（家宽 `114.94.40.209` → 热点 `58.41.90.133`）。另有 WireGuard（`TSINv2`）、Sangfor SSL VPN 两个虚拟网卡常驻。
- **结论：任何依赖「固定出口 IP 白名单」或「公网入站」的方案在本机都不可靠。** 要自动化就必须走**群机器人**（无 IP 要求、无需入站），或把发送逻辑放到**有固定公网 IP 的云服务器**上。
- 诊断命令备忘：

  - 外网可达性：check-host.net（先 `/check-tcp?host=IP:PORT` 拿 request_id，再轮询 `/check-result/<id>`，约需 30–40 秒）。

| **全天请假**（请假条目合计 = 8h） | 确保任务存在 **+ 自动创建模版行**（填报日期=目标日、实际投入=请假小时数、备注=任务名称/进展说明） |
| **混合日**（调休 3h + A 项目开发 5h = 8h） | **只确保任务存在，不自建模版行** → 按正常同步把工时分别落到各自项目下 |

> 用户原话（第 3 条）：「如果请假不是 8 小时，那就要检测下是不是满足总共 8 小时的要求，例如可以是调休 3 小时，A 项目开发 5 小时，这个就还是按正常去同步工时到对应的项目下即可」——**不要强行建【请假调休】去吃掉全部工时**。混合日的模版行留到确认页绑定。

⚠️ **全天请假必须改写条目归属**：创建完模版行后要把日报条目的 `projectNorm` / `project` 改写为解析出的真实项目，否则日报记「其它项目」、模版记「浙能法务二期」→ 匹配不上 → 落 `report_only=1 / 仅模版=1`，8h 同步不过去。

### 去重与反向关联

- **模版行去重**：`findExistingTpl()` 按「填报日期 + 任务名称 relation」匹配，命中即复用（日志打印【复用】），不重复建。
- **反向关联必做**：创建模版记录后必须把新记录 id 追加回任务行的「同步任务名称」，否则 rollup 公式不计算。


### 踩过的坑（勿再犯）

- **模版查询窗口**必须是 `min(目标日-3天, 今天-3天)`：原实现只按「目标日-3天」，导致**今天建的、目标日在 3 天后**的记录查不到（09-29/09-30 一度查不到模版）。
- **日报表 DB id** = `1a9c4392-b5ae-48f4-aa3b-e05135215dce`——注意是 **`aa3b`**，抄成 `aa4b` 会让全部查询 404「指定的页面不存在」（2026-09-25 踩过，排查了很久）。
- 用 Bash heredoc 写含 Windows 路径的 JS 会**吃掉反斜杠**（`C:\\Users\\` → `C:\Users\`），脚本静默失败 → 用 Write 工具写文件。
